# AI Explanations - osCommerce Online Merchant v2.3.4.1

## Section 1 – cc_validation::validate() (`catalog/includes/classes/cc_validation.php`)

- **Plain English**: Strips everything except digits from the card number, then guesses the card brand (Visa, Mastercard, Amex, etc.) by matching the number against a list of regexes. Next it checks that the expiry month is 1–12 and that the expiry year falls between this year and 10 years from now, then rejects cards that expired earlier this year. Finally it runs the Luhn checksum (`is_valid()`): double every second digit from the right, add up the digits, and accept the card if the total divides by 10.
- **Pattern**: Long `if / elseif` chain for brand detection, then sequential checks that return magic error codes (`-1` unknown brand, `-2` bad month, `-3` bad year, `-4` expired). Results are stored as object properties (`cc_type`, `cc_expiry_month`) as side effects.
- **Issues**: The brand table is out of date: Mastercard's 2-series numbers (2221–2720) are rejected, and the JCB pattern `3[0-9]{4}` is very broad. The year is built by gluing the first two digits of the current year onto the input, so it breaks if a 4-digit year is passed and around a century rollover. Negative-integer return codes force every caller to remember what each number means. There is no logging and no unit tests.
- **Improvements**: Move the brand rules into a data table (prefix ranges + lengths) that is easy to update. Return a result object or throw typed exceptions instead of magic numbers. Accept 2- or 4-digit years explicitly. Cover each brand and each failure path with unit tests. Better still, let the payment gateway's tokenised fields handle card data so the store never sees raw numbers.

## Section 2 – tep_db_perform() (`catalog/includes/functions/database.php`)

- **Plain English**: A generic helper that turns a PHP array into an SQL `INSERT` or `UPDATE`. The array keys become column names and the values become column values. The strings `'now()'` and `'null'` are treated specially and written as SQL keywords; every other value is escaped and wrapped in quotes. For updates, the caller passes the `WHERE` clause as a raw string.
- **Pattern**: Hand-rolled query builder using string concatenation, `while (list() = each())` loops and a "trim the trailing comma" trick (`substr($query, 0, -2)`).
- **Issues**: Column names and the `$parameters` WHERE clause are not escaped, so any caller that passes user input there opens an SQL injection hole. A real value of `'null'` or `'now()'` (e.g. a customer who types "null") silently becomes SQL `NULL`. The update branch has a typo, `$columns .= ' = null, '`, that only works by accident because it modifies the loop variable. `each()` was removed in PHP 8, so this function fatals on modern PHP.
- **Improvements**: Replace it with PDO or `mysqli` prepared statements with bound parameters. Whitelist column names against the table schema. Represent SQL expressions with an explicit marker object rather than magic strings. Swap `each()` for `foreach`.

## Section 3 – Stock update in checkout_process.php (lines ~145–183)

- **Plain English**: After the order is saved, the script loops over every product in the order. If stock tracking is on, it reads the current stock level (with a more complex join when the product is a downloadable file), subtracts the quantity bought, and writes the new number back. If stock drops below 1 and the store doesn't allow back-orders, it hides the product. It also adds the quantity to the product's "times ordered" counter.
- **Pattern**: Read-modify-write inside a loop, with nested feature-flag checks (`STOCK_LIMITED`, `DOWNLOAD_ENABLED`, `STOCK_ALLOW_CHECKOUT`) all in one 300-line procedural page script.
- **Issues**: Race condition: two customers checking out at the same moment both read the same stock level, and one update overwrites the other, so stock is oversold. There is no database transaction, so if the script fails halfway the order exists but stock, order lines and emails are only partly written. For products with attributes, only the first attribute (`$products_attributes[0]`) is used in the stock lookup. Configuration flags are compared as strings (`== 'true'`).
- **Improvements**: Use an atomic update (`UPDATE products SET products_quantity = products_quantity - ? WHERE products_id = ? AND products_quantity >= ?`) and check the affected row count. Wrap the whole order creation in a transaction. Extract the logic into an `InventoryService` class that can be unit-tested away from the page script.

## Section 4 – shoppingCart::restore_contents() (`catalog/includes/classes/shopping_cart.php`)

- **Plain English**: Runs when a customer logs in. It takes whatever the visitor put in their cart while logged out and saves it to the database: each product is inserted if new or has its quantity overwritten if already there, along with its options (size, colour, etc.). It then empties the in-memory cart, reloads the full cart from the database (merging old saved items with the new ones), removes invalid entries, and generates a new cart ID to detect tampering during checkout.
- **Pattern**: Two-way sync between session and database using nested loops with one query per product and per attribute (N+1 queries), relying on the `global $customer_id` variable.
- **Issues**: The number of queries grows with cart size (a select + insert/update per product, plus one per attribute, then one more per product on reload). No transaction, so a failure mid-way leaves a half-saved basket. If the same product is already in the saved basket, its quantity is overwritten rather than added, which can surprise users. Hidden dependency on a global variable makes the method hard to test.
- **Improvements**: Inject the customer ID and a repository object instead of using globals. Use `INSERT ... ON DUPLICATE KEY UPDATE` and batch-load attributes with a single `JOIN` query. Wrap the sync in a transaction. Decide and document the merge rule (add vs. replace quantities) and cover it with tests.

## Section 5 – tep_href_link() (`catalog/includes/functions/html_output.php`)

- **Plain English**: Builds every internal link in the store. It picks the HTTP or HTTPS base URL, appends the page name and query string, and adds the session ID to the URL when the visitor moves between the HTTP and HTTPS domains and cookies can't carry it. If "search-engine friendly URLs" is on, it turns `?`, `&` and `=` into slashes; otherwise it HTML-escapes `&`.
- **Pattern**: One function mixing URL building, session handling and HTML output, driven by global variables (`$request_type`, `$session_started`, `$SID`) and global constants.
- **Issues**: On a bad argument it calls `die()` and prints broken table HTML instead of raising an error. Putting the session ID in URLs leaks it through logs, bookmarks and the `Referer` header and enables session fixation. The SEO rewrite breaks any value that itself contains `=` or `&`. Returning HTML-escaped URLs means the same function can't safely be used for redirects. The cleanup loops (`while (strstr($link, '&&'))`) patch over sloppy input rather than building the query string correctly.
- **Improvements**: Build query strings with `http_build_query()` and escape only at output time in templates. Throw an exception on invalid input. Serve the whole site over HTTPS and use secure, `HttpOnly` cookies only, which removes the need for session IDs in URLs. Replace the SEO hack with proper routing (front controller + rewrite rules). Add unit tests for each connection and session combination.
